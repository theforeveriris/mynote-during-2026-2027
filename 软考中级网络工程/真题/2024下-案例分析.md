**参考答案**

| 空号 | 答案 | 说明 |
| ---- | ---- | ---- |
| （1） | 该接入口终端所属的 VLAN ID（10/20/30 之一，按表 1 与图 1 确定） | `port default vlan X`；原表缺失，**本空无法确定** |
| （2） | `trunk` | 0/0/4 为上联汇聚交换机的端口，需透传多 VLAN |
| （3） | `allow-pass` | `port trunk allow-pass vlan 10 20 30`，放行列表 |

- **Access 口**：连接终端，只属于一个 VLAN，用 `port default vlan X`；`vlan batch 10 20 30` 说明该交换机上存在三个业务 VLAN，接入口具体归属要看表 1 中 H1 各端口的 VLAN 规划。
- **Trunk 口**：连接上行设备（P1/P2），需携带多个 VLAN 的标签，`allow-pass` 后列出放行的 VLAN；若要求「仅放行」，还需 `undo port trunk allow-pass vlan 1` 去掉默认的 VLAN1。

**解析**

本题形式上考三条命令，实质上考「**端口角色决定端口类型**」：向下接终端是 Access，向上接汇聚是 Trunk。

三个高频失分点：

1. （1）凭猜测填 10——题干明确「按照上表的部署配置」，表未给出就不能定，考场必须查表；
2. （3）把 `allow-pass` 写成 `permit`（Cisco 风格）或 `allowed`；
3. 忘记 `vlan batch 10 20 30` 已经建好 VLAN，误以为要在接口下再建。

补充理解：Trunk 的 `pvid` 决定「不带标签的帧归哪个 VLAN」，上联口一般保持默认 VLAN1 或按规划设置；access 口发出的帧不带标签，终端无需支持 802.1Q。

**问题2**（6 分）

商场的无线系统采用 AC+FIT AP 模式时，请简述 AC 的主要配置内容。

**参考答案**

| 配置类别 | 主要内容 |
| -------- | -------- |
| 基础配置 | AC 管理 IP、到核心/网关的路由、与 DHCP 服务器互通、License（AP 数量授权）、时间同步 |
| AP 上线 | AP 认证方式（MAC 白名单/免认证）、AP 组（AP group）、AP 命名与位置标识、AP 固件版本统一、AP 上线状态确认 |
| 射频配置 | 射频模板（2.4G/5G 开关、频宽、信道、功率）、国家码、射频调优（自动信道/功率选择）、关闭低速率 |
| SSID/VAP 配置 | SSID 名称与隐藏、VAP 模板、业务 VLAN 绑定（商家/访客不同 VLAN）、转发模式（隧道转发/本地转发）、AP 与 VAP 的绑定关系 |
| 安全模板 | 认证方式（WPA2/WPA3-Enterprise 或 Portal）、加密算法（AES）、RADIUS/Portal 服务器地址与共享密钥、密钥更新周期 |
| 用户与策略 | 用户组与权限、带宽限速（每用户/每 SSID）、ACL（访客禁访内网）、DHCP 分配方式、漫游组 |
| 可靠性与运维 | AC 双机热备/VRRP、AP 双上行、CAPWAP 隧道保活、日志与告警、网管对接 |

**解析**

6 分题按「**AP 怎么上线 → 射频怎么发 → SSID 怎么绑 → 安全怎么认证 → 策略怎么控**」五段写，每段 1～2 条，得分最稳。

「AC 的主要配置内容」不是「AC 的作用」，答题必须落到**配置对象**（模板、组、绑定关系）上。写出「VAP 模板」「AP 组」「射频模板」「安全模板」这些华为 WLAN 的标准术语，比笼统写「配置 SSID 和密码」高一个档次。

本题的业务背景是「商家和访客权限不同」，因此**不同 SSID 绑不同 VLAN + ACL 隔离**是必答点。

**问题3**（4 分）

请列举常用无线认证方式，商场打印机和访客分别采用什么认证方式较为合适？

**参考答案**

（1）常用无线认证方式：

- **Open（开放）+ Portal（Web 认证）**：短信/微信/账号认证，适合访客；
- **WPA2/WPA3-PSK（预共享密钥）**：一网一口令，适合小型或固定设备场景；
- **WPA2/WPA3-Enterprise（802.1X + RADIUS）**：账号/证书认证，适合员工；
- **MAC 地址认证**：设备白名单，适合打印机、IoT 等哑终端；
- （补充）PPSK（每设备独立密钥）、短信认证、二维码认证；WEP 已不安全，不应使用。

（2）选型：

| 对象 | 推荐方式 | 理由 |
| ---- | -------- | ---- |
| 商场打印机 | **WPA2-PSK（预共享密钥）**，或 **MAC 认证 + 独立 SSID/VLAN** | 打印机通常不支持 802.1X 客户端与 Portal 交互，只能预置密钥或由 AC 做 MAC 白名单；同时应与顾客网络隔离 |
| 访客 | **Portal 认证（短信/微信）+ 独立访客 SSID/VLAN** | 免配置、可审计、可做时长/带宽限制，且与内网隔离，符合实名与安全管理要求 |

**解析**

这题考「**认证方式与终端能力的匹配**」。判断逻辑：

- 有浏览器、有人操作 → Portal 可行（访客）；
- 有 802.1X 客户端、有账号体系 → Enterprise（员工）；
- 哑终端（打印机、摄像头、POS）→ PSK 或 MAC 认证；
- 无任何认证 → Open，仅限完全公开场景，且必须做隔离与限速。

常见失分：给打印机选 Portal（打印机没有浏览器，无法弹认证页）；给访客选 802.1X（访客没有账号证书，体验极差）；只列认证方式不给出选型理由。

**问题4**（4 分）

当前配置的 AP 最大接入用户 ≤30，由于商场空间大，人流量大，计划通过缩小 AP 部署间隔、增加 AP 数量等方式，提升无线上网体验，请问该方式部署规划存在哪些缺点？应采用什么措施解决？

**参考答案**

（1）缺点（答出 2～3 点）：

- **同频干扰加剧**：AP 密度过高、覆盖重叠过大，2.4GHz 仅有 1/6/11 三个非重叠信道，信道复用距离不足，空口冲突与重传上升，速率反而下降；
- **漫游频繁（乒乓效应）**：终端在相邻 AP 间反复切换，切换开销与丢包增加，语音/视频体验变差；
- **单 AP 功率被迫降低、覆盖碎片化**：为压制干扰而调低功率，边缘覆盖变差，出现覆盖空洞与「假信号」；
- **成本与施工压力**：AP、PoE 端口、布线、License 成倍增加，管理与运维复杂度上升；
- **容量未必提升**：空口是共享介质，AP 增多但信道不增，整体吞吐存在上限。

（2）解决措施：

- **射频规划与自动调优**：信道/功率自动调优（RRM），2.4G 只用 1/6/11，优先 5GHz；必要时调整频宽（80MHz→40MHz）以增加可用信道；
- **提高单 AP 容量**：选用 Wi-Fi 6/6E 高密度 AP（多射频、MU-MIMO、OFDMA），而不是单纯堆数量；
- **负载均衡**：开启 AP 间负载均衡，按用户数/流量引导终端接入，避免单 AP 过载；
- **容量与勘测先行**：按「并发终端数 ÷ 单 AP 目标接入数」计算 AP 数量，现场勘测/仿真确定点位，控制覆盖重叠度（约 15%～20%）；
- **分层覆盖**：高密度区域（中庭、餐饮区）用定向天线/室分系统，普通区域降低密度；
- **有线补强**：固定商户、收银、办公位优先有线接入，减少无线压力；
- **统一漫游策略**：同一 AC/漫游组、启用 802.11r/k/v，减少切换开销。

**解析**

本题是「**堆 AP 不等于加容量**」的经典反问。无线是共享介质，容量取决于「信道数 × 单信道效率 × 空间复用」，盲目加密 AP 只会让同频干扰与漫游开销吃掉收益。

答题框架：缺点按「干扰—漫游—覆盖—成本」四条写，措施按「频谱（信道/频宽/5G）—设备（Wi-Fi 6/定向天线）—策略（负载均衡/漫游）—规划（勘测/容量计算）」四条对应。每条缺点最好配一条措施，形成闭环。

加分点：写出「2.4G 只有 3 个非重叠信道」这一硬约束，以及「先算容量再定点位」的规划顺序。

### 1.3 案例3 网关 ACL、勒索病毒与链路扩容

> 考点：防火墙/ACL 规则设计、勒索软件识别与处置、等价路由与链路聚合、哈希算法与流量分担

某企业网络拓扑如图 1，网络规划详见表 1。所有业务网关均位于交换机 Core 上，有线终端、无线终端、无线 AP 均由 DHCP 服务器分配 IP 地址及网络参数。

**问题1**（4 分）

管理员在 Core 上规划了 ACL，需求如下：

1. 只允许无线、有线终端访问 DNS 服务器的 DNS 服务。
2. 禁止无线用户访问设备管理、无线 AP 管理网络。

请补充下表中的空缺项：

`[原文为图/表，需对照原卷]`（ACL 规划表未收录，表中规则行与待填空格缺失，**本题各空无法确定答案**）

**参考答案**

原表未收录，无法逐空作答。以下给出**规则的填写逻辑与顺序要求**：

| 序号 | 源 | 目的 | 协议/端口 | 动作 | 说明 |
| ---- | -- | ---- | --------- | ---- | ---- |
| 1 | 无线用户网段 | 设备管理网段 + AP 管理网段 | IP（any） | **deny** | 需求 2，必须放在 permit 之前 |
| 2 | 无线用户网段 | DNS 服务器地址 | UDP 53、TCP 53 | **permit** | 需求 1（无线） |
| 3 | 有线终端网段 | DNS 服务器地址 | UDP 53、TCP 53 | **permit** | 需求 1（有线） |
| 4 | 无线/有线网段 | DNS 服务器地址 | IP（any） | **deny** | 只允许 DNS 服务，其他服务一律拒绝 |
| 5 | any | any | any | **deny**（或默认拒绝） | 兜底 |

关键点：

- **顺序**：ACL 自上而下匹配、命中即停。需求 2 的 deny 必须排在需求 1 的 permit **之前**，否则无线用户先命中 permit，隔离失效；
- **粒度**：需求 1 要求「只允许 DNS 服务」，因此 permit 必须限定 `udp 53`（以及 `tcp 53`，用于大响应与区域传送），并追加一条针对同一目的地址的 deny，防止其他端口被放行；
- **地址对象**：源为无线/有线终端网段，目的为 DNS 服务器主机地址（`0.0.0.0` 反掩码 或 host 形式），管理网段包含「设备管理 VLAN + AP 管理 VLAN」两段；
- **应用方向**：ACL 需在 Core 的对应 Vlanif 或全局 `traffic-filter` 下调用，方向为终端侧入方向。

**解析**

本题原文的 ACL 表未收录，具体空值须对照原卷。

需要掌握的核心只有两句：**「ACL 是顺序匹配、命中即停」** 与 **「先拒绝、后允许」**。凡是同时出现「允许某服务」和「禁止某类访问」的题，deny 规则一定在上。

另一个易错点：需求 1 的「只允许 DNS 服务」有两层含义——既要放行 53 端口，又要拒绝该目的的其他端口；只写一条 permit 53 是「允许但不限制」，不满足「只允许」。

DNS 同时用 UDP 53（常规查询）和 TCP 53（大响应、区域传送），只写 UDP 会被判不完整。

**问题2**（8 分）

网管员发现某台主机感染了病毒，大部分的文件后缀都变成了 `.LOCK`，桌面背景被篡改，提示「your data has been locked, mail to …」。该主机可能感染（5）类型的病毒，网管员应采取的（6）措施（至少回答 3 点措施）。

**参考答案**

（5）**勒索病毒（勒索软件，Ransomware）**，具体为文件加密型勒索病毒。

（6）处置措施（答出 3 点即可，按「止血—取证—恢复—加固」组织）：

- **立即断网隔离**：拔掉网线/禁用无线/关闭共享，防止加密继续扩散到网络共享与服务器；
- **保留现场、不支付赎金**：不要重启或格式化，保留样本、日志与加密文件用于溯源（支付赎金不保证解密，且助长犯罪）；
- **从离线/异地备份恢复**：用未受感染的备份恢复数据，验证备份完整性；
- **全网排查横向移动**：检查同网段主机、域控、文件服务器是否被植入，排查 RDP/SMB/弱口令等入口；
- **清除与重装**：用杀毒/EDR 全盘查杀，无法清除则重装系统并打补丁；
- **封堵入口与加固**：关闭不必要的 445/3389 端口与外网映射，修补永恒之蓝等高危漏洞，禁用宏，强口令 + MFA；
- **邮件与终端防护**：邮件网关拦截恶意附件，终端部署 EDR，关闭不必要的共享与 Autorun；
- **制度与演练**：3-2-1 备份策略（3 份副本、2 种介质、1 份离线）、最小权限、定期恢复演练、安全培训。

**解析**

识别勒索病毒看三个特征：**文件被加密改名（.LOCK 等后缀）+ 勒索提示 + 桌面壁纸被篡改**。答「木马/蠕虫/宏病毒」都不到位，因为题干的核心是「数据被加密勒索」。

处置题的采分逻辑是「**先止血、再恢复、后加固**」：一上来就写「杀毒」是典型错误——病毒还在运行，杀毒会与加密进程抢时间，先隔离才是第一分。

「至少 3 点」是硬要求；能写出「不支付赎金」「离线备份」「排查横向移动」三点，基本满分。

**问题3**（8 分）

网络使用一段时间后，用户反馈互联网业务变慢，网络管理员发现 NGFW 和 Core 之间下行带宽长时间利用率 100%，计划利用空闲的千兆端口，在 NGFW 和 Core 之间增加一条链路，实现链路带宽扩容以解决网络故障。

网管员规划以下两种扩容技术方案：

方案一：原有链路不变，两台设备之间新增链路采用新的互联地址，通过配置静态路由形成（7）从而实现两条链路的流量负载。

方案二：采用链路聚合技术，将原有链路和新增链路捆绑在一起形成一条逻辑链路，实现链路带宽的提升。为防止接收端接收到的数据包乱序，可采用（8）负载机制，既能保证同一数据流在同一条物理链路上转发，又实现了各物理链路上的负载分担。

网络管理员选择方案二进行配置，防火墙的链路聚合配置如下：

```text
[NGFW] interface eth-trunk 1
[NGFW-Eth-Trunk1] trunkport gigabitethernet 0/1
[NGFW-Eth-Trunk1] trunkport gigabitethernet 0/2
[NGFW-Eth-Trunk1] load-balance src-dst mac
[NGFW-Eth-Trunk1] port link-type trunk
[NGFW-Eth-Trunk1] port trunk allow-pass vlan 100
```

交换机 Core 的链路聚合配置与防火墙相同，配置完成后，网管员发现网络体验并未得到改善，查看物理链路、聚合链路状态均正常，但流量依然集中在原有的链路上，新增链路几乎无流量。请分析其原因是（9），可采取（10）措施解决该故障。

**参考答案**

| 空号 | 答案 | 说明 |
| ---- | ---- | ---- |
| （7） | 等价路由（ECMP，等价多路径） | 两条静态路由目的相同、开销相同，形成负载分担 |
| （8） | 逐流（per-flow，基于流的） | 同一数据流固定走同一物理链路，避免乱序；不同流之间分担 |
| （9） | 两端均配置 `load-balance src-dst mac`，而 NGFW 与 Core 之间流量的**源/目的 MAC 固定不变**（就是两台设备互联口的 MAC），哈希计算结果唯一，所有流量被映射到同一条成员链路 | 也可补充：两端哈希模式不一致时同样会集中 |
| （10） | 将两端负载分担模式改为**基于 IP**（`load-balance src-dst ip`，或 `src-ip`/`dst-ip`），并保证两端模式一致；必要时结合 `src-dst port` | 使不同 IP 流分散到不同成员链路 |

补充说明：

- 方案一（等价路由）实现简单，但需要额外地址规划，且故障切换依赖路由收敛，回程路径也需成对配置；
- 方案二（链路聚合/Eth-Trunk）是二层捆绑，逻辑上是一条链路，带宽叠加、故障切换快，但**两端必须配置相同的负载分担模式**；
- 聚合模式（手工负载分担 / LACP）也需两端匹配，LACP 模式下还要注意系统优先级与活动端口数。

**解析**

本题的「坑」全在最后一段现象：**链路状态正常，但新链路没流量**。这说明聚合本身建立成功，问题出在「流量怎么分」——即哈希算法。

哈希负载分担的逻辑是：对报文的特征字段做哈希，用哈希值选择成员口。当特征字段恒定（NGFW 与 Core 直连时，报文的源/目的 MAC 永远是这两台设备接口的 MAC），所有流的哈希值相同，自然全压一条链路。解法只能是**换更细的哈希因子**（源/目的 IP，甚至端口），让不同会话落到不同链路。

高频失分：

1. （7）答「负载均衡」而不答「等价路由」——本题是**静态路由**形成的等价路径，关键词必须是 ECMP/等价路由；
2. （8）答「负载分担」而不答「逐流」——题目强调「防止乱序」，对应的是 per-flow 而非 per-packet；
3. （9）只答「配置错误」不指出「src-dst mac 在直连场景下恒定」这一机理；
4. （10）只说「改配置」，不说改成什么模式、两端要一致。

**问题2**（4 分）

当上述 4 台路由器均正确配置接口 IP 地址，建立 OSPF 邻居关系，并将接口宣告到规划区域，完成 OSPF 路由收敛后，在路由器 R1 上执行 `ping -a 192.168.0.1 34.1.1.4`，结果显示 "Request time out"。请说明原因，并简要说明如何解决该故障（非静态路由解决措施）。

**参考答案**

原因：

- `ping -a 192.168.0.1` 指定以 **R1 的 LoopBack0 地址**为源，报文能到达 34.1.1.4（去程有路由：LSDB 中 R2 已产生 `Sum-Net 34.1.1.0`，R1 学到区域间路由），但 **34.1.1.4 所在路由器上没有回到 192.168.0.1 的路由**，ICMP Reply 无法返回，表现为 `Request time out`；
- 回程缺失的根因是 **LoopBack0 网段未被正确宣告进 OSPF**（未宣告、宣告到了错误区域，或该区域与 R4 所在区域之间没有连通路径）。若 LoopBack0 被宣告进了与骨干区域不连通的非骨干区域（如 Area 3），其它区域同样学不到该 /32 主机路由。

解决（非静态路由）：

1. 在 R1 上把 LoopBack0 网段宣告进 OSPF 的骨干区域（或与其它区域连通的区域）：

```text
[R1] ospf 1
[R1-ospf-1] area 0
[R1-ospf-1-area-0.0.0.0] network 192.168.0.1 0.0.0.0
```

2. 若 R1 的某个区域（如 Area 3）**未与 Area 0 直接相连**，在被割裂的 ABR 上配置**虚连接**，把该区域逻辑上接入骨干：

```text
[R1] ospf 1
[R1-ospf-1] area 1
[R1-ospf-1-area-0.0.0.1] vlink-peer 2.2.2.2
```

3. 检查区域划分与 `network` 宣告是否一致，确保 LoopBack0 所在区域与 R4 所在区域之间可通过骨干区域交换 Type 3 LSA。

**解析**

「能 ping 通别人、别人 ping 不回我」是**回程路由**问题，不是去程问题。本题用 `-a` 指定了源地址，等于人为把「源」换成了一个可能没被通告的地址，故障因此暴露。

判断路径：

1. 看 LSDB：`Sum-Net 34.1.1.0` 说明去程有路由 → 排除「不可达」；
2. 既然去程通、回程不通，就查**源地址是否被通告**：LoopBack0 是 /32，若没写进 OSPF，别的路由器就没有这条主机路由；
3. 若已宣告仍不通，查**区域连通性**：非骨干区域必须通过 Area 0 中转，Area 3 若与 Area 0 不连续，需要虚连接。

常见失分：把原因写成「链路故障」「ACL 阻断」（题干无此信息）；解决措施写「加静态路由」——题干明确排除。

**问题3**（6 分）

所有路由器都完成相关配置后，R1～R4 互通，R4 和 R5 互通，但是路由器 R1 上执行 `ping -a 12.1.1.1 172.16.0.2`，结果显示 "Request time out"。请补齐以下代码片段，实现 R1 和 R5 互通。

```text
[R4-ospf-1]（7）      //在R4将外部路由引入OSPF
```

完成上述配置后，还需要在 R5 进行配置（8）才能实现 R1 和 R5 互通。

在 R4 将外部路由引入到 OSPF 时，R4 会成为（9）路由器，R4 会触发 2 条 LSU，第一条 LSU 携带自身的 type 1 LSA，且 ASBR 置位，R3 收到这条 LSA 后，会转换为（10）LSA，传递到其他区域；第二条 LSU 携带（11）LSA，其作用是（12）。

**参考答案**

| 空号 | 答案 | 说明 |
| ---- | ---- | ---- |
| （7） | `import-route direct`（若 R5 侧通过静态路由到达则为 `import-route static`；按图确定） | 把 R4 上 R5 方向的路由引入 OSPF |
| （8） | 在 R5 上配置**回程路由**：一条指向 R4 的静态路由（或默认路由） | 如 `ip route-static 0.0.0.0 0.0.0.0 <R4接口地址>`，R5 不运行 OSPF 时必须手工指回程 |
| （9） | ASBR（自治系统边界路由器） | 引入外部路由的路由器 |
| （10） | Type 4（ASBR-Summary LSA，ASBR 汇总 LSA） | 由 ABR 产生，通告「如何到达 ASBR」 |
| （11） | Type 5（AS External LSA，外部 LSA） | 携带外部路由 |
| （12） | 描述**外部路由**（AS 外部目的地）及到达该目的地的度量/转发地址，由 ASBR 产生并泛洪到整个 AS（Stub/NSSA 区域除外），使其它区域路由器获知外部网段 | — |

配置示例：

```text
[R4] ospf 1
[R4-ospf-1] import-route direct
[R4-ospf-1] quit

[R5] ip route-static 0.0.0.0 0.0.0.0 <R4接口地址>
```

**解析**

本题考「**OSPF 与外部网络互通的两半**」：一半在 ASBR（引入），一半在外部设备（回程）。只做引入，R1 能到 R5，但 R5 的回包无处可去，仍然 ping 不通——这正是题干「R4 和 R5 互通、R1 到 R5 不通」的原因。

LSA 部分是固定考点，务必记牢「谁产生、传多远、装什么」：

| LSA | 名称 | 产生者 | 范围 | 内容 |
| --- | ---- | ------ | ---- | ---- |
| Type 1 | Router LSA | 每台路由器 | 本区域 | 本机链路与开销 |
| Type 2 | Network LSA | DR | 本区域 | 广播网段与接入路由器 |
| Type 3 | Network Summary | ABR | 其它区域 | 区域间网段 |
| Type 4 | ASBR Summary | ABR | 其它区域 | 到 ASBR 的路由 |
| Type 5 | AS External | ASBR | 整个 AS（Stub/NSSA 除外） | 外部路由 |
| Type 7 | NSSA External | ASBR（NSSA 内） | NSSA 内 | 外部路由，ABR 转 Type 5 |

「R3 收到 Type 1 后转换为 Type 4」的机理：R3 是 ABR，它要把「ASBR 在哪里」告诉其它区域，于是产生 Type 4 指向 R4 的 Router-ID。

**问题4**（4 分）

请简要概述当 OSPF 的非骨干区域配置为 stub 特殊区域后 LSA 的变化。

**参考答案**

配置为 Stub 区域后：

1. **Type 4（ASBR-Summary）与 Type 5（AS External）LSA 不再注入该区域**：ABR 会阻止这两类 LSA 泛洪进 Stub 区域，区域内的路由器看不到外部路由明细；
2. **ABR 自动向该区域下发一条 Type 3 的默认路由（0.0.0.0/0）**，区域内路由器通过这条默认路由访问外部网络；
3. **Type 1、Type 2、Type 3 仍然保留**：区域内拓扑与区域间网段路由正常传播；
4. 因此 Stub 区域内的 LSDB 规模显著减小，路由器 CPU/内存开销降低，拓扑变化对外部路由的影响被屏蔽；
5. 注意：Stub 区域**不能是骨干区域 Area 0**，且区域内不能有 ASBR（不能配置 `import-route`）；完全 Stub（Totally Stubby）还会进一步过滤 Type 3，只保留一条默认路由。

配置示例：

```text
[R3] ospf 1
[R3-ospf-1] area 2
[R3-ospf-1-area-0.0.0.2] stub
```

**解析**

Stub 的采分点就两句话：**「4、5 类不进，ABR 发默认路由」**。答出这两点基本满分，再补「1/2/3 类保留」「减小 LSDB」更完整。

易错点：① 以为 Stub 会过滤 Type 3（那是 Totally Stubby/NSSA 的行为差异，NSSA 是引入 Type 7）；② 以为 Stub 区域可以放 ASBR（不允许，因为不能有 Type 5）；③ 把默认路由说成 Type 5（Stub 内是 ABR 产生的 Type 3 默认路由）。

NSSA 的对比记忆：**NSSA 允许 ASBR 存在，外部路由以 Type 7 在区域内传播，ABR 再转换为 Type 5 送出**；Stub 则完全不允许外部路由进入。

### 2.2 高频结论速记

| 场景 | 结论 |
| ---- | ---- |
| 端口类型 | 下接终端 Access（`port default vlan`）；上联汇聚 Trunk（`allow-pass`） |
| ACL 顺序 | 自上而下、命中即停；**先 deny 后 permit** |
| 只允许某服务 | 放行该端口 + 对同目的追加 deny，UDP 与 TCP 都要写 |
| 勒索病毒特征 | 文件改后缀（.LOCK）+ 勒索提示 + 壁纸篡改 |
| 勒索处置 | 断网隔离 → 保留现场/不付赎金 → 备份恢复 → 排查横向 → 加固 |
| 静态路由扩容 | 等价路由（ECMP）负载分担 |
| 聚合乱序 | 逐流（per-flow）分担 |
| 聚合有链路无流量 | `src-dst mac` 在直连场景哈希恒定 → 改 `src-dst ip`，两端一致 |
| OSPF 反掩码 | `network 12.1.1.0 0.0.0.255`；Loopback 用 `0.0.0.0` |
| ping -a 不通 | 回程路由缺失（源地址未被通告/区域不连通） |
| ASBR | 引入外部路由 → Type 1 置 ASBR 位；ABR 产生 Type 4 |
| 外部路由 | Type 5（NSSA 内为 Type 7），Stub/NSSA 不注入 |
| Stub | Type 4/5 不进，ABR 下发 Type 3 默认路由；1/2/3 保留 |

### 2.3 答题模板

**模板一：ACL 设计**

```text
1. 列需求 → 每条需求翻译成「源 + 目的 + 协议/端口 + 动作」
2. 排序 → 所有 deny（隔离类）放最前，permit（服务类）随后，最后兜底 deny
3. 调用 → Core 的 Vlanif / 全局 traffic-filter，方向为终端侧入方向
4. 检查 → 是否「只允许」？是否有 UDP+TCP 双协议？管理网段是否含 AP 管理？
```

**模板二：安全事件处置**

```text
止血：断网/隔离/封 IP 与域名
取证：保留日志、样本，不重启不格式化
恢复：离线备份恢复，验证完整性
根治：补丁、口令、关闭端口与共享、最小权限
长效：EDR、邮件网关、3-2-1 备份、演练与培训
```

**模板三：链路扩容/负载分担**

```text
方案对比：等价路由（三层、需地址规划、靠路由收敛）
         链路聚合（二层、带宽叠加、毫秒切换、两端模式须一致）
排障口诀：链路 UP 无流量 → 查哈希因子是否恒定 / 两端模式是否一致
```

**模板四：OSPF 综合**

```text
配置：ospf 进程 router-id → area X → network 网段 反掩码
排障：先看邻居（display ospf peer）→ 再看 LSDB（display ospf lsdb）
      → 去程有路由就查回程（源地址是否被通告、区域是否连通）
引入：ASBR import-route → Type 5 泛洪；ABR 产生 Type 4 指路
特殊区域：Stub（无 4/5，有默认）｜NSSA（有 7，ABR 转 5）
```
