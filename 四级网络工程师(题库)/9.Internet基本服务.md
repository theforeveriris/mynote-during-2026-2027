
## 1.应用进程响应并发请求分类

服务器处理客户端请求的方式主要分为以下两类：
- 重复服务器
    - 采用"先进先出"（FIFO）原则处理请求
    - 服务器按顺序依次处理每个客户端请求，处理完一个请求后再处理下一个
    - 结构简单，但当某个请求处理时间较长时，后续请求会被阻塞
    - 适用于处理时间短、计算量小的请求
- 并发服务器
    - 每收到一条请求，服务器就创建一个子进程（或线程）来专门处理该请求
    - 主进程继续监听新的连接请求，子进程负责与客户端通信
    - 能够同时处理多个客户端请求，响应速度快
    - 资源消耗较大，每个子进程都需要独立的内存空间和系统资源
    - 适用于处理时间长、计算量大的请求

## 2.对等计算机模型（P2P）基本结构

在P2P模型中，每个计算机都是一个节点，节点之间直接通信，没有中心服务器。

集中式P2P
- 存在一个中心服务器，但服务器通常只存储目录和索引信息，不存储实际的文件内容
- 文件传输直接在节点之间进行
- 典型代表：Napster(这是一个基于P2P模型的音乐分享平台)
- 优点：结构简单，搜索效率高
- 缺点：中心服务器是单点故障，一旦服务器瘫痪整个网络将失效；存在法律风险

> Napster 是互联网历史上第一个被广泛使用的点对点（P2P）文件共享平台，由肖恩·范宁（Shawn Fanning）和肖恩·帕克（Sean Parker）于 1999 年创办。

>它彻底改变了人们获取和分享音乐的方式，也是数字音乐时代的开创者之一。

> Napster 虽被关闭，但它推动了后续去中心化 P2P 技术（如 BitTorrent、eMule）的发展，同时也倒逼了传统音乐产业转型，为后来的 iTunes 音乐商店以及 Spotify 等流媒体平台的崛起奠定了基础。

分布式非结构化P2P
- 无中心节点，节点随机连接形成随机图结构
- 支持复杂查询和模糊查询
- 采用泛洪（Flooding）机制进行搜索：节点将查询请求转发给所有邻居节点，邻居节点继续转发
- 利用TTL（生存时间）机制控制泛洪范围，防止查询报文无限传播
- 典型代表：Gnutella（这是一个基于P2P模型的文件分享系统）
- 优点：无单点故障，支持灵活查询
- 缺点：泛洪产生大量网络流量，搜索效率低，可扩展性差

> Gnutella 是互联网历史上第一个真正实现完全去中心化（分布式非结构化）的 P2P（点对点）文件共享网络协议，于 2000 年由 AOL 旗下的 Nullsoft 公司员工开发。

> 与 Napster 这类依靠中央服务器记录索引的“集中式 P2P”不同，Gnutella 完全摆脱了对中央服务器的依赖。

> 为了解决泛洪机制带来的网络拥塞问题，后期的 Gnutella（以及改进版 Gnutella2）引入了 “超级节点”（Ultrapeers/Supernodes） 机制，将性能较强的节点升级为局部索引中心，从而大幅提升了搜索效率。典型客户端包括 Limewire、BearShare 和 Cabos 等。

分布式结构化P2P
- 无中心节点，采用分布式散列表（DHT，Distributed Hash Table）技术
- 将资源映射到哈希空间，每个节点负责一部分哈希空间
- 仅支持精确关键字匹配查询，不支持模糊查询
- 具有良好的可扩展性，查询效率高（通常为O(log N)）
- 维护复杂，需要处理节点加入和离开时的数据迁移
- 典型代表：Pastry(这是一个基于P2P模型的文件分享系统)、Tapestry(这是一个基于P2P模型的文件分享系统)、Chord、CAN

> Pastry 是计算机网络中一种经典的分布式结构化 P2P（点对点）重叠网络协议，于 2001 年由 Antony Rowstron 和 Peter Druschel 提出。

> 它基于分布式散列表（DHT，Distributed Hash Table）技术构建，核心用于在无中心节点的对等网络中实现高效的资源定位与路由。

混合式P2P
- 结合了集中式和分布式的优点
- 将节点分为超级节点（索引节点）和普通节点
- 超级节点维护其所辖普通节点的索引信息，负责搜索和路由
- 典型代表：Skype、BT（BitTorrent）、PPLive
- 优点：搜索效率高，可扩展性好，兼顾了集中式和分布式的优势

| 结构类型 | 中心节点 | 查询方式 | 可扩展性 | 典型代表 |
|---------|---------|---------|---------|---------|
| 集中式 | 有 | 向中心服务器查询 | 差 | Napster |
| 分布式非结构化 | 无 | 泛洪搜索 | 较差 | Gnutella |
| 分布式结构化 | 无 | DHT精确匹配 | 好 | Chord、Pastry |
| 混合式 | 超级节点 | 超级节点间路由 | 好 | Skype、BT |



## 3.3. 域名解析方式

域名系统（DNS）用于将人类可读的域名（如http://www.example.com）转换为机器可识别的IP地址。

解析方式分类
- 递归解析
    - 客户端向本地域名服务器发出请求后，本地域名服务器负责完成整个解析过程，最终将结果返回给客户端
    - 一次完成，客户端只需发送一次请求
    - 本地域名服务器负担较重
- 反复解析（迭代解析）
    - 本地域名服务器向根域名服务器发出请求，根服务器返回下一级服务器的地址，本地服务器再向下一级服务器请求，如此反复多次，直到获得最终结果
    - 分层多次解析，每次服务器返回的是"下一步去哪里查询"的指引
    - 减轻单个服务器的负担

域名服务器工作原理
- 每一个域名服务器至少知道根服务器的IP地址及其父节点服务器的IP地址
- 本地域名服务器（Local DNS）是用户计算机配置的首选DNS服务器，通常由ISP提供
- 解析过程从本地域名服务器开始，通过迭代解析或递归解析，最终获得最终结果

提高域名解析效率的方法
- 从本地域名服务器开始解析：避免每次都从根服务器开始查询
- 域名服务器使用高速缓存技术：将之前解析过的域名-IP映射关系缓存起来，相同域名的后续查询可直接从缓存中获取结果
- 主机采用高速缓冲技术：操作系统和浏览器也会缓存DNS解析结果，减少向DNS服务器发送请求的次数
- 缓存条目都有生存时间（TTL），过期后需要重新解析，以保证数据的时效性

## 4. 域名对象类型

DNS资源记录（Resource Record）定义了不同类型的域名对象：

| 记录类型 | 名称 | 功能说明 |
|---------|------|---------|
| A | 主机记录 | 将域名映射到IPv4地址，是最常见的记录类型 |
| AAAA | 主机记录 | 将域名映射到IPv6地址 |
| MX | 邮件交换记录 | 指定接收该域名邮件的邮件服务器及其优先级 |
| PTR | 指针记录 | 用于反向解析，将IP地址映射回域名 |
| CNAME | 别名记录 | 为域名设置别名，一个域名可以有多个CNAME记录 |
| SOA | 授权开始记录 | 标识区域的起始授权信息，每个区域文件必须有且仅有一个SOA记录 |
| NS | 名称服务器记录 | 指定负责该区域的域名服务器 |
| HINFO | 主机信息记录 | 描述主机的CPU类型和操作系统信息 |
| TXT | 文本记录 | 存储任意文本信息，常用于SPF验证等 |


## 5. 远程登录（Telnet）

网络虚拟终端（NVT）
- Telnet协议通过定义网络虚拟终端（NVT，Network Virtual Terminal）来解决不同终端类型的兼容性问题
- NVT是一种标准的、抽象的终端格式，将不同厂商、不同操作系统的本地终端统一起来
- 客户端将本地终端的输入转换为NVT格式发送给服务器，服务器将NVT格式的输出转换为本机终端格式
- 通过NVT，任何类型的终端都可以与任何类型的远程主机进行通信

工作原理
- 基于TCP连接，默认端口号为23
- 采用客户端/服务器模型
- 用户在本地终端输入的命令被发送到远程主机执行，执行结果返回并显示在本地终端上
- 由于Telnet传输的数据（包括用户名和密码）以明文形式传输，存在安全风险，现已被SSH（Secure Shell）所取代

## 6. FTP服务

FTP（File Transfer Protocol，文件传输协议）是用于在网络上进行文件传输的标准协议。

基本模型
- 采用客户端/服务器（C/S）模型
- 利用TCP建立双向连接，包括两个独立的连接：
    - 控制连接：用于传输命令和响应，端口号为21，在整个会话期间保持连接
    - 数据连接：用于传输文件数据，端口号为20（主动模式下），按需建立和关闭

连接建立方式
- 主动模式（Active Mode）
    - 客户端向服务器的21端口建立控制连接
    - 客户端通过PORT命令将自己的数据端口号告知服务器
    - 服务器主动从20端口向客户端指定的端口发起数据连接
    - 在客户端位于防火墙或NAT后面时可能无法正常工作
- 被动模式（Passive Mode）
    - 客户端向服务器的21端口建立控制连接
    - 客户端向服务器发送PASV命令，请求进入被动模式
    - 服务器打开一个临时端口并告知客户端
    - 客户端主动向服务器的临时端口发起数据连接
    - 适用于客户端位于防火墙后面的场景


文件传输方式
- 文本文件传输（ASCII模式）
    - 对文件进行格式转换，以适应不同操作系统的文本格式差异（如换行符的不同）
    - 适用于传输纯文本文件
- 二进制文件传输（BINARY模式）
    - 不对文件格式进行任何变化，按照原始文件相同的位序以连续比特流方式进行传输
    - 适用于传输可执行文件、图片、音频、视频等非文本文件
    - 保证文件内容的完整性

常见命令：
| 命令 | 功能 |
|------|------|
| delete | 删除远程主机上的文件 |
| pwd | 显示远程主机的当前工作目录 |
| get | 从远程主机下载文件 |
| put | 向远程主机上传文件 |
| ls | 列出远程主机当前目录的文件列表 |
| cd | 切换远程主机的目录 |
| lcd | 切换本地主机的目录 |
| binary | 切换到二进制传输模式 |
| ascii | 切换到ASCII传输模式 |
| quit | 退出FTP会话 |


## 7. 电子邮件系统

电子邮件系统由用户代理、邮件服务器和邮件传输协议组成。

SMTP（Simple Mail Transfer Protocol）
- 简单邮件传输协议，工作在TCP之上，默认端口号为25
主要用于服务器之间的邮件传递，以及用户代理向邮件服务器发送邮件
- 采用"推"（Push）模式，将邮件从发送方推送到接收方
- 基于ASCII文本，早期不支持传输二进制数据，后通过MIME扩展支持

POP3（Post Office Protocol version 3）
- 邮局协议第3版，默认端口号为110（加密版本为995）
- 用于从用户从邮件服务器读取邮件
- 采用"拉"（Pull）模式
- 工作流程分为三个阶段：
    - 认证阶段：用户输入用户名和密码进行身份验证
    - 事务处理阶段：用户可以查看、下载、删除邮件
    - 更新阶段：用户发出Quit命令后，服务器删除标记为删除的邮件，释放资源

IMAP（Internet Message Access Protocol）
- 互联网消息访问协议，默认端口号为143（加密版本为993）
- 与POP3类似，用于从邮件服务器读取邮件
- 支持在服务器上管理邮件（创建文件夹、标记已读等），邮件保留在服务器上
- 适合多设备访问同一邮箱的场景

电子邮件报文格式
- RFC 822：定义了电子邮件报文的基本格式，包括报头和报文体
- MIME 1.0：定义了电子邮件报文的MIME类型，扩展了RFC 822，支持传输非ASCII文本、二进制数据、多媒体内容等

POP3常用命令：
| 命令 | 功能 | 所属阶段 |
|------|------|---------|
| USER | 提供用户名 | 认证阶段 |
| PASS | 提供用户邮件口令（密码） | 认证阶段 |
| STAT | 查询邮箱中报文总数和总长度 | 事务处理阶段 |
| LIST | 列出邮箱中每个报文的编号和长度 | 事务处理阶段 |
| RETR | 获取指定编号的邮件内容 | 事务处理阶段 |
| DELE | 标记指定邮件为删除 | 事务处理阶段 |
| RSET | 复位，删除所有删除标记，中止当前操作 | 事务处理阶段 |
| NOOP | 无操作，用于保持连接 | 事务处理阶段 |
| QUIT | 退出，进入更新阶段 | 更新阶段 |


## 8. Web服务

Web服务是Internet上最广泛应用的服务之一，基于HTTP协议提供超文本信息浏览功能。

HTML（HyperText Markup Language）
- 超文本标记语言，用于定义Web页面的结构和内容
- 是页面规范的基本解释单元
- 能够对请求和返回进行页面翻译，将标记语言转换为可视化的页面内容显示在浏览器中
- 支持超链接，实现页面之间的跳转


HTTP（HyperText Transfer Protocol）
- 超文本传输协议，是客户机和服务器之间的传输协议
- 建立在TCP连接之上，默认端口号为80（HTTPS为443）
- 是一个面向对象的协议，精确定义了请求报文和响应报文的格式
- 采用请求/响应模型：客户端发送请求，服务器返回响应
- HTTP/1.0为短连接，每次请求/响应后关闭连接；HTTP/1.1默认使用持久连接（Keep-Alive）


URL（Uniform Resource Locator）
- 统一资源定位器，用于标识Internet上资源的位置
- 格式：协议://主机名:端口号/路径/文件名
- 例如：http://www.example.com:80/index.html

Web安全性
- SSL协议（Secure Sockets Layer）
    - 工作在传输层，位于TCP/IP协议与各类应用层协议之间
    - 提供加密通信，防止第三方偷看内容
    - 提供数据完整性校验，防止第三方篡改数据
    - 提供身份认证机制
    - 现已被TLS（Transport Layer Security）所取代，但习惯上仍称为SSL
- CA证书（Certificate Authority）
    - Web服务器向CA认证中心申请数字证书，证明自己的身份
    - 浏览器内置了受信任的CA根证书，用于验证服务器证书的真实性
    - 证书包含服务器的公钥、域名、有效期等信息


浏览器组成
- 控制单元：解释键盘/鼠标输入命令，处理用户交互
- 客户单元：负责与Web服务器建立连接，发送HTTP请求，接收HTTP响应
- 解释器单元：解析HTML文档，渲染页面内容并显示

Web服务器
- 保存大量的Web页面（HTML文件、图片、视频等）
- 接受和处理浏览器的HTTP请求
- 实现HTTP服务器功能，返回相应的响应
- Web服务器不具备编辑Web页面的功能，页面编辑需要使用专门的网页编辑工具


## 9. Web安全性

保护计算机的方法
- 浏览器将Internet世界划分成几个安全区域：Internet区域、本地Intranet区域、可信站点区域、受限站点区域
- 对不同区域设置不同的安全级别，限制ActiveX控件、脚本等的执行

验证站点真实性
- 利用Web站点传来的数字证书进行验证
    - 浏览器检查证书是否由受信任的CA签发，证书中的域名是否与访问的域名一致，证书是否在有效期内

避免他人假冒自己
- 用户可以在CA安全认证中心申请自己的数字证书
    - 将证书安装在浏览器中，用于身份认证和数字签名
    - 在需要身份验证的场景中，向服务器出示自己的证书

避免第三方篡改或偷看
- 使用安全套接层技术（SSL/TLS）建立加密通道
    - 所有在客户端和服务器之间传输的数据都经过加密，第三方无法窃听或篡改
    - HTTPS = HTTP + SSL/TLS

保证传输机密性
- 将Web站点放入浏览器的可信站点区域
    - 可信站点区域的安全级别较低，允许更多的交互，但同时要求站点使用加密通信

防止病毒传播
- SSL/TLS技术主要用于加密通信和身份认证，并不能直接防止病毒传播
- 防止病毒传播需要依靠杀毒软件、防火墙、浏览器安全设置等综合措施
- 不要下载和运行来源不明的文件，定期更新系统和软件补丁


## 10. 网络蠕虫与木马

网络蠕虫（Worm）
- 是一种独立的恶意程序，不需要依附于其他程序
- 通过网络漏洞进行传播，能够自我复制和主动传播
-  早期蠕虫利用电子邮件传播，现代蠕虫利用操作系统漏洞、应用程序漏洞、弱密码等多种方式传播
- 典型特征：独立性、自我复制能力、主动传播能力
- 著名案例：Morris蠕虫（1988年）、冲击波蠕虫、震荡波蠕虫、Conficker蠕虫等
- 危害：消耗网络带宽和系统资源，导致网络拥塞和系统瘫痪


木马（Trojan Horse）
- 是一种伪装成正常程序的恶意程序
- 没有自我复制能力，需要用户主动下载和执行
- 通常 由控制端和被控端组成，攻击者通过控制端远程操控被感染的计算机
- 主要目标：窃取敏感信息（如密码、银行账号）、远程控制计算机、植入后门
- 与蠕虫的区别：木马不自我复制，不进行主动传播，需要诱骗用户执行


| 特性 | 网络蠕虫 | 木马 |
|------|---------|------|
| 独立性 | 独立程序 | 依附于正常程序 |
| 自我复制 | 有 | 无 |
| 传播方式 | 主动传播，利用漏洞 | 被动传播，诱骗用户执行 |
| 主要目的 | 消耗资源、造成破坏 | 窃取信息、远程控制 |
